pso-blender local wiki / iff

IFF chunks documented, implemented (shared utility, not a standalone file type)

Not a file extension of its own - a generic chunk container convention used inside other formats (.bml items, NJ model data) to sequence typed, sized blocks of data one after another.

Confirmed

  • IffHeader: a 4-byte ASCII type_name tag plus a U32 body_size - the classic "4CC + length" chunk header shape.
  • IffChunk (iff.py) is a small writer built on the same AbstractFileArchive/ResizableBuffer plumbing .rel uses - opens a chunk, writes its body, backpatches body_size once the body's real length is known.
  • parse_pof0 handles a specific chunk type used for pointer-fixup data ("POF0") seen in real NJ model data - relocation info for the chunk stream, conceptually parallel to .rel's own pointer table but scoped to one IFF chunk stream instead of a whole file.

Cross-reference: pso_ultimate_importer

  • Their parse_pof0 (_archives/pso_ultimate_importer-main/__init__.py:2160) spells out a concrete encoding this addon's own iff.py doesn't document in detail: POF0 is a variable-length delta stream, not a flat pointer-offset list. Each entry is 1-3 bytes; the top 2 bits of the first byte select the width (1/2/3 bytes total), the remaining bits hold a delta that's always multiplied by 4 (pointers are 4-byte aligned) and added to a running cumulative offset - a single 0x00 byte ends the table. Worth cross-checking against this addon's own POF0 handling if it's ever suspected of a bug, since the delta/cumulative-offset shape is easy to get subtly wrong.
  • Their apply_pof0_relocation also has to infer the payload's base address (not stored anywhere explicit) by checking which raw pointer values already fall inside the payload versus which look too large - a heuristic worth remembering if this addon's own POF0 handling ever needs the same trick on data with an unknown base.

pso-blender local wiki / tam

.tam documented, implemented (import + export)

Frame-swap texture animation data - a fixed set of .xvm texture-array positions cycled over time (screens, neon signs, lava, waterfalls, etc.). Imported as real Blender Image Sequences that preview correctly in the 3D viewport.

Confirmed

  • Big-endian on Blue Burst, unlike most of this addon's other little-endian formats - called out directly in code as a gotcha (tam.py: ".tam files are big endian on blue burst.....").
  • Structure: a TamEntry per animation - frame_type (SLIDESHOW is the only kind this addon writes), animation_id, frame_count, and a list of Keyframe (texture_index + frame_delay) - one keyframe per frame of the animation, texture_index pointing at the paired .xvm's array position for that frame.
  • animation_id is written from Texture.animation_instance_id, not Texture.id - a shared/deduplicated texture id would otherwise collide two unrelated placements' independent timing data onto one animation entry. See .xvm for the full id-vs-instance-id distinction.
  • Per-object playback speed round-trips through export and is editable via "Animation Frame Delay" in Material Properties.

Open / hypothesis

  • UV-scroll texture animation (MeshTreeFlag.HAS_UV_ANIMATION in .rel) is a separate mechanism from the frame-swap animation this format covers, and is not yet imported or exported at all. One weak, explicitly-hedged lead found on pioneer2.net's "PSO Dev Wiki Staging Thread" (forum user Kion, speculating about classic NJCM/.nj strip-chunk "user offset bytes"): "I think they're used during run time to manage which texture is being used for a triangle to handle scrolling textures... the user offset bytes are only included in the mines" - explicitly a guess ("I think"), about a different mesh format (classic NJCM, not n.rel's chunk system), and claimed Mines-only. Not strong enough to treat as confirmation of anything about this addon's own HAS_UV_ANIMATION bit, but the only hit found anywhere on this topic.
  • Timing-accurate viewport preview of animation speed is deferred by choice - currently uniform in the 3D viewport regardless of each animation's real per-frame delay.
Cross-reference: checked pso_ultimate_importer (_archives/pso_ultimate_importer-main/__init__.py) for any .tam/frame-swap texture animation handling - none found, no matches for "tam", "texture anim", "frame delay", or "slideshow". That addon doesn't appear to support this mechanism at all.

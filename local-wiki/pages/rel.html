.rel documented, implemented (import + export)

A map's core geometry file(s). Exporting a map named foo can produce up to three separate files - only whichever ones the current scene actually has matching objects for (REL Settings: render/collision/minimap):
FileContents
foon.relrender geometry - what the player actually sees
fooc.relcollision geometry - invisible, walkable/solid surfaces
foor.relminimap geometry

Confirmed - container format (all three)

  • Not a flat/fixed-table format like .gsl - a relocatable pointer format. rel.py's Rel class is a generic write-time buffer: every Serializable item written into it has its outgoing pointer fields tracked, and a pointer relocation table is emitted at the end so the game can fix up absolute addresses once the file is loaded into memory. serialization.py (Serializable, Ptr32, Numeric, FixedArray) is the shared struct-packing machinery every REL-family dataclass builds on.
  • n_rel.py = render REL, c_rel.py = collision REL, r_rel.py = minimap REL. Each defines its own dataclass tree on top of the shared Rel/Serializable plumbing - they are related but structurally distinct formats, not three views of one shared schema.

Confirmed - n.rel (render) specifics

  • Chunks: n.rel splits a map into spatial Chunk entries (position + radius), each owning a MeshTree (and optionally an animated_mesh_trees pointer - see Open below). The game only renders a chunk when the camera is within radius of its center - this is a real, visible culling boundary, not just an optimization hint.
  • Chunk radius bug, fixed: the real game's per-chunk radius is consistently much larger than "distance to the furthest member object's center" (confirmed on real map data - a measured case computed ~2200 from geometry vs. the file's real stored value of only ~374.5, i.e. the opposite direction of what you'd assume - real files use *generous* radii, not tight ones). Underestimating it caused whole chunks to flicker in/out of existence as the camera rotated. Fix: on a re-export of an already-imported map, trust the original file's stored radius (chunk_radius stashed on the collection at import time) instead of recomputing from geometry; only fall back to a geometry-based approximate radius for a freshly authored chunk with no round-trip data.
  • A chunk always covering the whole map (always_rendered_chunk, radius 999999.0) exists separately from the ordinary position/radius-culled chunks - used for geometry that must never cull out.
  • The mesh geometry a chunk's MeshTree points into is not stored in n.rel itself - see .xj, the actual vertex-buffer/material format a render MeshTreeNode points at.

Confirmed - Chunk.animated_mesh_trees' real byte layout, cracked (2026-08-30)

Background: a second, separate MeshTree pointer per chunk, presumed to be for animated/moving mesh objects (doors, etc. - MeshTreeFlag has HAS_UV_ANIMATION/HAS_TEXTURE_ANIMATION bits). Long-standing gap: not imported or exported by this addon.

  • Quantified on real data first (acity): map_acity00_00n.rel has 33 animated mesh trees across 5 of its 6 chunks (154 static ones total - animated content is 17.6% of all trees by count: chunk 10: 5, chunk 20: 9, chunk 30: 4, chunk 40: 4, chunk 41: 11). A full import-then-export round trip through this addon (no edits) shrinks the file from 607136 to 545958 bytes - 61178 bytes (10.1%) silently dropped - the concrete, measured cause behind "zero-edit REL export isn't byte-identical" (see below) for at least this map.
  • Two community leads pointed the same direction but stalled on the same detail: pso_ultimate_importer's GameCube parser reads a parallel "animated" list per section with one extra field vs. the static one; the psodevwiki mirror's Schthack notes independently describe the same "Format A / Format B" split and guess the extra field is "probly pointer to the movement data" - neither source decoded it further, both marked it FIXME.
  • Solved directly, empirically, without needing either source to finish the job: since this addon's own Chunk dataclass already declares animated_mesh_trees as the exact same type as static_mesh_trees (Ptr32[MeshTree]), the obvious first experiment was just running the existing static- tree parser (xj.xj_to_blender_mesh) against it unchanged. Result: exactly every other entry parsed into real, plausible mesh geometry (4-288 vertices) and every other one crashed with a garbage offset - a very characteristic "wrong stride" signature, not random corruption.
  • The real stride is 32 bytes, not 16 - a real MeshTree (16 bytes: root_node/unk1/texture_animation_info/tree_flags, unchanged) sits in the first half of each 32-byte animated entry, followed by 16 bytes of extra per-entry data no other format has documented anywhere. Verified by literally re-running the static mesh importer against every animated tree in acity with this layout: 33 of 33 parsed successfully, 0 failures - real doors/mechanism geometry loads today, this is no longer theoretical.
  • The extra 16 bytes, first look (acity's 33 entries only, so treat as a single data point, not a general rule yet): byte-identical across every entry except one bit - a leading float32 that's 0.2 every single time (plausibly a shared animation speed/duration), 8 zero bytes, then a trailing u32 that's either 0x200000 or 0x200001 (a single low bit differs, meaning not yet known). Whether 0.2 is truly universal or just constant within this one file needs checking against other maps before reading anything more into it.
  • Doors are NOT part of this animated-mesh list conceptually, but their geometry now looks like it is - from newserv: doors are ordinary ObjectSetEntry records in .dat (full field layout and door-type-ID table written up there), with open/close driven by quest switch-flag state via .evt's set_switch_flag/clear_switch_flag opcodes - not a toggle inside n.rel. Best current synthesis, now on firmer ground: animated_mesh_trees is the moving prop's actual geometry (now readable), .dat/.evt is the gameplay logic deciding when to play it (already solved) - the .bml model-lookup problem is the one piece still missing to connect a specific door instance to which of these animated trees (if any) is actually its moving mesh.

Confirmed - MeshTree.unk1 is a real pointer, not a scalar (2026-08-30)

Background: unk1 ("has something to do with UV animations") sits on the ordinary static MeshTree struct, always 0 except on trees with MeshTreeFlag.HAS_UV_ANIMATION set, where it's consistently a small multiple of 24 (0, 24, 48, 240, 264, 288, 360, 384, 408 seen on real acity chunk 20 data) - the working theory going in was "index into a local table," but an extensive brute-force search (150,000+ candidate base offsets across the whole file, two plausibility filters) found zero matches for that shape.

  • Cross-checked against the file's own pointer relocation table instead of guessing further - decoded `.rel`'s footer-based reloc table directly (Rel. POINTER_TABLE_POINTER_OFFSET/POINTER_COUNT_OFFSET at -0x20/ -0x1C from file end; the table itself turned out to be a flat array of u16 dword-deltas - each entry × 4, summed cumulatively from 0 - not the POF0-style variable-length delta scheme IFF/POF0 uses, a different in-house scheme for this container format). Checked whether unk1's own file position appears in that table the same way root_node's does: it does, on every UV-animated tree checked - and texture_animation_info's position (NULL on these same trees) does not appear, consistent with "null pointers are omitted from the relocation table." Confirms unk1 is genuinely Ptr32-typed in the real format, just declared as a plain U32 in this addon's dataclass so far.
  • Dereferencing it two levels deep leads to a PAIR of named strings, not a numeric speed/direction: payload_offset + unk1 lands on a small intermediate record shaped (0, name_ptr_A, 0, 0, name_ptr_B, 0) - both non-null pointer slots lead to null-terminated ASCII names, not a single lone reference as first thought. Real pairs pulled from acity: g032_Box03a ↔ g032_hand, g032_machine ↔ g032_rifle, g064_uv_p0 ↔ g064_uv_p1, g128_kabe02 ↔ g128_kabe02_2. No numeric field anywhere in this 24-byte record - it's purely two name references.
  • User's hypothesis (2026-08-30), fits the evidence well: maybe there's no stored speed/direction value at all because none is needed - the pair names two related nodes (start/end, fixed/moving, or similar) and the game derives the UV scroll's direction (and possibly rate) directly from those two named nodes' own positions/orientations in the model hierarchy, the same way the mesh geometry itself already defines everything else. Consistent with what's actually in the file: a (name, name) pair, not a `(name, vector)` or `(name, float)` one. Not proven outright, but a real numeric parameter was searched for (brute-force, see above) and never found anywhere nearby - this reframes that as expected rather than still-missing.
  • Directly connects to an older, previously unconnected mystery: the very first pass at animated_mesh_trees (before this session's 32-byte-stride breakthrough) found its own a_ofs field pointing at "mixed content - name strings like 'g032_hand'/'g032_Box03a', and separately real 3D coordinates" - same naming convention (g0XX_...), never explained at the time, and even the exact same name (g032_hand) turning up again here. Strong hint the game engine has one shared named-node-pairing mechanism reused by both the UV-scroll system (static trees) and the moving-mesh system (animated trees) - not two unrelated features. The "separately real 3D coordinates" half of that old finding isn't explained by this pass - still open, and now the natural next thing to check (do those coordinates belong to one of these same named nodes?).
  • Still not fully closed: whether the pairing genuinely IS the whole mechanism (no numeric parameter anywhere) versus a numeric value still hiding somewhere this pass didn't look isn't proven either way - e.g. the game could still look up a per-name-pair speed from a separate, not-yet-found table at runtime rather than deriving it purely from geometry. Enough real evidence now (two solid names, zero numeric fields, on 18/18 real samples) to treat "no stored speed" as the leading theory rather than an open guess, though.
  • Bigger discovery, following the same lead further: those name pairs aren't a dedicated UV-animation structure at all - they're just two entries drawn from one big, shared name table for the whole map. A plain byte-level scan for null-terminated identifier-shaped strings ([a-z][a-z0-9_]{4,}, immediately followed by 0x00 - the same "classic strings utility" technique, just restricted to this format's actual naming convention instead of any printable ASCII, which was mostly false positives from ordinary mesh/vertex binary data) found 245 such names on real acity data, every one of them sitting in a single contiguous ~4KB region (0x91dbe-0x92dac) - clearly one deliberate table, not scattered incidental strings. Covers essentially every named prop/wall/floor/sign/monitor piece used anywhere in the map (n128_buildwall01, o128_s_monitor01, n128_warpwall01, ...) - and includes at least one unambiguous door reference, h32_hnt_door04. Full list saved outside this repo at pso-blender-external-notes/acity_rel_name_table.json (245 names + region bounds) for future keyword searches without re-running the scan.

  • Yes, these names are tied to real positions - not through a separate lookup array (checked: the file bytes immediately around the name table are the pointer relocation table itself, no room for a parallel position array there), but through the ordinary mechanism this addon already uses for everything else: the position of the tree that references the name pair (root_node's local x/y/z, combined with its chunk's own world position). Confirmed on real data - three UV-animated trees in acity chunk 20 (tutu_g/tutu_o, uv_b0, uv_p0) sit at local positions (332, 38, 108.5), (294, 28.5, 108.5), (294, 47.5, 108.5) - visibly close together (same X/Z, small Y offsets), consistent with several small UV-animated sub-parts of one physical assembly placed right next to each other.
  • Tried the same scan against a real .bml - clean negative result: ran the identical identifier-shaped-string technique against every item in bm_obj_city_common.bml (model bytes, texture list, texture archive, and .njm animation data - all 35 entries, including door-named ones like fd_obj_shopdoor_01, hunter_door, fe_hntdoor_fusagi) - zero real matches anywhere, only float-byte coincidences. Makes sense: .bml already names each model at the archive/filename level, so it never needed an internal string table the way one map-spanning .rel does to cross-reference many named sub-parts within itself. This name table and .bml filenames don't share a direct textual link - the .dat-type-ID-to-.bml-model connection, if it exists beyond a hardcoded client table, isn't this.
  • Now wired into real import, not just a scratch script (2026-08-30) - n_rel.py's static-tree loop resolves MeshTree.unk1's name pair whenever HAS_UV_ANIMATION is set and embeds the first available name into the Blender object's own name (e.g. 20_1_g032_Box03a_node_0 instead of a bare 20_1_node_0), plus both names stashed as obj["pso_uv_part_name_a"/"_b"]. Verified on three real maps: acity (18 objects renamed), aforest01 (0 - correctly finds none, that map has no UV-animated content at all, consistent with the theme), acave01 (37 - thematically coherent names like domagma_taki "lava waterfall" and bridge01/bridge02, confirming the mechanism generalizes past acity's city-specific content).
  • Checked whether the same rename could apply to animated trees - not yet, different structure: AnimatedMeshTree.unk1 is confirmed to be a real pointer too (same relocation-table check as the static case), and is very likely the GameCube-derived a_ofs field from the original animated_mesh_trees investigation (same struct position, right after the mesh pointer) - but it does not lead to a name pair. Dereferenced directly (as an absolute offset, not payload-relative like the static case), it lands on a differently-shaped record: (nearby_ptr, small_count, type_flag=0x2000B or 0x30007, ...) - e.g. counts like 120, 300, 1000, 2400 seen on real acity data. Plausibly the "separately real 3D coordinates" half of the old mixed-content finding (movement/keyframe data?) rather than another name table - not decoded yet, a distinct open thread from the static-tree naming work above. Dereferenced nearby_ptr one level further: not a flat float array (checked directly, first 64 bytes are all zero/NaN when read as floats) - it contains yet more embedded pointers, including one pointing back at nearby_ptr's own address. `type_flag` seen so far: 0x20003 (acity chunk 20's trees) and 0x30007 (chunk 40/41's) - two distinct values, plausibly two different sub-kinds of this record. Genuinely deeper/different structure than the static-tree case - paused here rather than continuing to guess blind; a fresh dedicated pass (probably starting from the GC `a_ofs` cross-reference again, now with a concrete "nested pointers, not flat data" shape to test against) is the natural way back in.

Open / hypothesis

  • A zero-edit REL export is not yet byte-identical to the original file - now mostly explained by the above for at least acity (tracked separately, see rel_export_branch.md for the detailed coverage/diff tooling).
  • c.rel/r.rel field-level layout isn't written up here yet - see c_rel.py/r_rel.py directly for now (they're reasonably self-documenting dataclasses).
  • Not yet implemented in the addon itself: this section documents a successful throwaway-script experiment, not a merged code change - n_rel.py's real import/export still only knows about static_mesh_trees.

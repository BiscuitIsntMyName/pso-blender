pso-blender local wiki / rel

.rel documented, implemented (import + export)

A map's core geometry file(s). Exporting a map named foo can produce up to three separate files - only whichever ones the current scene actually has matching objects for (REL Settings: render/collision/minimap):
FileContents
foon.relrender geometry - what the player actually sees
fooc.relcollision geometry - invisible, walkable/solid surfaces
foor.relminimap geometry

Confirmed - container format (all three)

  • Not a flat/fixed-table format like .gsl - a relocatable pointer format. rel.py's Rel class is a generic write-time buffer: every Serializable item written into it has its outgoing pointer fields tracked, and a pointer relocation table is emitted at the end so the game can fix up absolute addresses once the file is loaded into memory. serialization.py (Serializable, Ptr32, Numeric, FixedArray) is the shared struct-packing machinery every REL-family dataclass builds on.
  • n_rel.py = render REL, c_rel.py = collision REL, r_rel.py = minimap REL. Each defines its own dataclass tree on top of the shared Rel/Serializable plumbing - they are related but structurally distinct formats, not three views of one shared schema.

Confirmed - n.rel (render) specifics

  • Chunks: n.rel splits a map into spatial Chunk entries (position + radius), each owning a MeshTree (and optionally an animated_mesh_trees pointer - see Open below). The game only renders a chunk when the camera is within radius of its center - this is a real, visible culling boundary, not just an optimization hint.
  • Chunk radius bug, fixed: the real game's per-chunk radius is consistently much larger than "distance to the furthest member object's center" (confirmed on real map data - a measured case computed ~2200 from geometry vs. the file's real stored value of only ~374.5, i.e. the opposite direction of what you'd assume - real files use *generous* radii, not tight ones). Underestimating it caused whole chunks to flicker in/out of existence as the camera rotated. Fix: on a re-export of an already-imported map, trust the original file's stored radius (chunk_radius stashed on the collection at import time) instead of recomputing from geometry; only fall back to a geometry-based approximate radius for a freshly authored chunk with no round-trip data.
  • A chunk always covering the whole map (always_rendered_chunk, radius 999999.0) exists separately from the ordinary position/radius-culled chunks - used for geometry that must never cull out.
  • The mesh geometry a chunk's MeshTree points into is not stored in n.rel itself - see .xj, the actual vertex-buffer/material format a render MeshTreeNode points at.

Open / hypothesis

  • Chunk.animated_mesh_trees - a second, separate MeshTree pointer per chunk, presumed to be for animated/moving mesh objects (doors, etc. - MeshTreeFlag even has HAS_UV_ANIMATION/HAS_TEXTURE_ANIMATION bits). Not imported or exported yet. See also the .dat/.evt investigation - originally suspected to be door-related, turned out to be a separate mechanism (enemy spawn/event-script variants), so the door-animation lead is still open and unconnected to that finding.
    Useful cross-reference found in pso_ultimate_importer (_archives/pso_ultimate_importer-main/__init__.py, parse_stage, ~line 2865): it parses a GameCube-version n.rel ("Flipper" format, big-endian - a related but not identical platform variant from Blue Burst's) and explicitly reads two lists per section/chunk: list_a (static meshes) and list_b (animated meshes) - a strong hint list_b is the GameCube analog of our own animated_mesh_trees. Its per-entry layout, 32 bytes: mesh_ofs (U32), a_ofs (U32), 8 bytes, speed (F32), 8 bytes, flags (U32) - matches this addon's own earlier finding on real acity data (see the backlog). Entries whose flags match a small skip-set (0x010244, 0x010204 for the animated list) are deliberately not read by that importer - presumably non-renderable or special-cased mesh types. Treat as a strong lead, not gospel - GC and BB are related but distinct formats, not verified identical.
    Second, independent confirmation - psodevwiki mirror (github.com/jakeprobst/psodevwikibackup, a live git mirror of the now-dead sharnoth.com/psodevwiki - pages/format/n_rel.txt and pages/format/n_rel/schthack_notes.txt): the 52-byte Section Table Entry really does carry two parallel offset/count lists - "Format A" (static) and "Format B" (animated) - right next to each other, matching this addon's own Chunk.animated_mesh_trees theory. Schthack's own original mapviewer notes (reproduced verbatim in that mirror) label the animated one's fields VertexB_Off/VertexB_Count and say outright "this one is the animated one," and note Format B's entry has one extra dword vs. Format A that Schthack guesses is "probly pointer to the movement data." Neither source decodes that extra dword further - both mark it FIXME, same place this addon's own investigation stalled.
  • Doors are NOT part of this animated-mesh list - a real correction to the original theory, from newserv: doors are ordinary ObjectSetEntry records in .dat (full field layout and door-type-ID table now written up there), with open/close driven by quest switch-flag state via .evt's set_switch_flag/clear_switch_flag opcodes - not a toggle inside n.rel at all. Best current synthesis: the n.rel animated-mesh list is likely the door's (or other moving prop's) actual moving geometry - what to render while it's opening - while the separate .dat/.evt system (documented, working) is the gameplay logic deciding when that animation should play. Both pieces are probably needed for a complete picture; only the gameplay-logic half is solved so far.
  • A zero-edit REL export is not yet byte-identical to the original file (tracked separately, see rel_export_branch.md for the detailed coverage/diff tooling).
  • c.rel/r.rel field-level layout isn't written up here yet - see c_rel.py/r_rel.py directly for now (they're reasonably self-documenting dataclasses).

pso-blender local wiki / xj

.xj documented, implemented (import + export)

The actual mesh/material format a render n.rel's MeshTree points into - vertex buffers, index buffers, and render-state opcodes (blend mode, texture addressing, and critically which texture). Also used standalone (paired with its own .xvm) for NPCs/objects/items, as an alternative container to .bml.

Confirmed

  • Container level: literally an NJTL + NJCM (+ POF0) IFF chunk stream - confirmed directly in this addon's own xj.py (IffChunk("NJTL"), IffChunk("NJCM")) and independently in pso_ultimate_importer's actor importer, which parses the same three chunk tags for .xj. So at the container/chunk-tag level, .xj and .nj/NJCM really do share the same tagging scheme - the two are not as unrelated as the file extensions suggest. See the open discrepancy below for where they actually diverge.
  • This addon's XjMesh/VertexBuffer/IndexBuffer is a vertex-buffer-based mesh encoding (explicit vertex formats, index buffers, per-material RenderStateArgs) - used specifically for map render geometry and standalone object/NPC/item meshes. This addon treats it as structurally distinct from the classic triangle-strip-based NJ/NJCM mesh encoding used inside a .bml's per-item models - same chunk tag, different payload shape (see below).
  • 7 vertex formats (VertexFormat1-7, xj.py), built by composable inheritance of VertexWithPos/VertexWithUv/ VertexWithNormal/VertexWithColor - which fields a given mesh's vertices carry (position always, plus any combination of UV/normal/vertex-color) determines which format number it's written as.
  • TEXTURE_ID render state is a raw array index into the paired .xvm's texture list, confirmed via this addon's own read/write pipeline (xj_xvm.xvrs[tex_id]) - not a lookup by a stable ID. This is why REL export has to be careful to preserve original array *positions*, not just original texture *content* - see .xvm for the full story (this was the source of a real correctness bug this addon had to work around).
  • RenderStateArgs/RenderStateType (xj.py) carry the per-material state a real map/object actually uses - blend mode, texture addressing mode, and the texture ID above.

Open discrepancy - cross-reference: pso_ultimate_importer

  • Their NinjaXJImporter.readMesh (_archives/pso_ultimate_importer-main/__init__.py:1654) treats the NJCM chunk's mesh payload as the classic triangle-strip encoding: a vertex_info_list (per-list vtype flags for uv/normal/color) plus two triangle-strip lists (triangle_strip_list_a/_b) - the same shape their shared NinjaChunkMixin uses for classic DC/GC NJ chunk data, and notably with no per-material render-state block (blend mode, texture addressing) - unlike this addon's RenderStateArgs. That's a real structural mismatch with this addon's own vertex-buffer/index-buffer/render-state XjMesh implementation, not just a naming difference.
  • Their _MODEL_EXTS = {'.nj', '.gj', '.xj'} groups .xj alongside DC's .nj and GC's .gj as "the same role, one model per file, one extension per platform" - consistent with how this addon uses .xj, and a useful confirmation of its role even where the internal mesh encoding disagrees.
  • A dedicated pioneer2.net (Ephinea forum) thread, "Xj Conversion Notes" (7 pages, last post 2016, author appears to have abandoned it before reaching a conclusion) leans toward the same classic-NJCM/triangle-strip reading - but its detail is about NJCM in general, it's unclear the thread ever specifically nailed down that this is what BB's .xj uses (as opposed to other platforms' model formats), and no render-state/blend-mode/texture-addressing structure was found described anywhere in it. Low-confidence, doesn't really move the needle either way.
  • Not resolved. This addon's own .xj reader/writer is shipped and exercised against real Ephinea (PC/Blue Burst) files - the stronger signal here - while pso_ultimate_importer's model-parsing code is explicitly scoped to DC/GC in several other places (see .bml's cross-reference note) and may simply not have a correct BB/PC vertex-buffer path. Neither newserv's docs, the psodevwiki mirror (no xj page exists there at all), nor the pioneer2.net thread above settle it. Worth a deliberate side-by-side byte check on one real .xj file someday rather than assuming either side is right from this alone.

Related settings

  • "XJ Settings" (Material Properties panel, xj_material_properties_menu.py) is where this addon exposes the per-material knobs that end up encoded here and in the paired .xvm: blend mode, per-axis texture addressing, Generate Mipmaps, Alpha Compression, Force Uncompressed, and the source .xvm path used by standalone Export XVM.

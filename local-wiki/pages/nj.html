NJ / NJCM / NJTL / NJM core mesh implemented, NJM export experimental

SEGA's classic chunk-based "Ninja" model format family, used inside .bml for NPC/object/item models - a different mesh representation from the vertex-buffer-based .xj that map render geometry uses. Four related files split the format by concern:
FileRole
nj.pyVertex/mesh chunk data (NjMesh) and conversion to/from a Blender mesh
njcm.pyScene-graph node tree (MeshTreeNode, eval flags) tying meshes together with transforms/hierarchy
njtl.pyTexture list - name/pointer table associating a model with its textures
njm.pySkeletal animation (keyframes) - experimental export only, per the README

Confirmed

  • NinjaEvalFlag (njcm.py) - per-node bitflags controlling how a MeshTreeNode's transform/children get evaluated: UNIT_POS/ UNIT_ANG/UNIT_SCL (ignore that transform component), HIDE, BREAK (stop tracing children), SKIP, SHAPE_SKIP, CLIP, MODIFIER.
  • njm.py's KeyframeF/KeyframeI carry an id plus 3 float or int components - float keyframes for continuous values (translation), int keyframes presumably for discrete ones; MData3 groups multiple keyframe tracks (translations, ...) for one animated node.
  • Object parenting on import creates a matching Blender node hierarchy; empty objects create meshless nodes (per README).

Cross-reference: pso_ultimate_importer

  • Their NinjaChunkMixin.readChunks confirms classic NJ/NJCM's opcode shape: each chunk is a (type, config) byte pair, an NJD_CE value ends the stream, and NJD_CN is a no-op/continue - useful if nj.py's own reader/writer ever needs cross-checking against another implementation.
  • Much more detail on NJM than this addon currently documents or imports - their parse_njm (_archives/pso_ultimate_importer-main/__init__.py:3808) parses both the DC/GC NMDM-magic variant and a separate Blue Burst "player format" with no leading magic: instead, the last 16 bytes of the file hold an indirection chain (offset1 -> action_offset -> motion_start) to locate the actual motion header - worth checking against real BB .njm data, since this addon's own njm.py doesn't document a footer-based layout at all yet.
  • Motion header fields they read: m_data_table_rel (i32), frame_count (i32), motion_type (u16, a channel bitmask - 0x0001=position, 0x0002=euler, 0x0004=scale, 0x2000=quaternion, each present bit appending one column to the keyframe table in that order), and inp_fn (u16, whose low byte is the interpolation type: 0=Linear, 1=Spline).
  • Rotation values use the same 2*pi/65536 fixed-point-angle convention seen elsewhere in this addon's own code (e.g. n.rel's chunk rotations) - a small but useful confirmation that this angle encoding is a shared PSO-wide convention, not something specific to one format.

Cross-reference: pioneer2.net forum user "kion" (2015-2020)

Medium-high confidence for a forum source: kion was writing working extraction tooling across a 5-year span (not just recalling from memory), and posted concrete structs each time. Still a single hobbyist, not a maintained parser - treat as a strong lead to verify against real files, not gospel.

  • Open discrepancy with pso_ultimate_importer's own claim above: kion's 2019 post gives inp_fn as a 2-bit-field interpolation selector - 0x0000=linear, 0x0040=spline, 0x0080=user function, 0x00C0=mask - which disagrees with pso_ultimate_importer's "low byte: 0=Linear, 1=Spline" claim above. Two independent community sources, two different bit layouts for the same field - neither verified against real data yet, flagged rather than picked.
  • Keyframe layout differs by platform, per kion's 2019 post: DC/PC use {u32 keyframe; i32 angle[3]} for rotation keyframes, while "PSO BB, typically" uses a narrower {u16 keyframe; u16 angle[3]} (angle = raw value / 0xFFFF × 2π, the same fixed-point-angle convention noted above). Motion type flags: 0x01=position, 0x02=rotation, 0x04=scale.
  • His 2015 thread (extracting all 341 PC v2 player animations from PlyMotionData.pr2) independently confirms a leading NMDM magic + frame count for that particular container, and that a POF0 ("P0F0" in his notes) chunk marks the true end of useful data - anything after it is discardable padding.
  • Partial tension with pso_ultimate_importer's "BB player format" footer-indirection theory (see above): kion's 2019 post treats BB NJM as differing from DC/PC only in keyframe field width, still under the same NMDM-prefixed structure - not a magic-less, footer-indexed file. But a separate 2020 post from the same author, about assets embedded in .rel (not standalone .njm), independently confirms the exact *pattern* pso_ultimate_importer describes: seek to EOF-16 for a header-table pointer, a list of pointers to embedded assets, each formatted as normal .nj/.njm data but without the IFF header. Plausible reconciliation: standalone/`.bml`-embedded NJM (has NMDM) vs. REL-embedded motion assets (no magic, footer-indexed) may simply be two different container conventions within BB, not a contradiction about NJM itself - flagged as unresolved rather than resolved either way.
  • Richer NJCM/NJTL structural detail than previously listed (same 2019 thread): a full njcm_object_t (eval_flags, mesh_offset, pos/rot/scale, child/sibling offsets) and njcm_mesh_t (vertex/polygon chunk offsets, bounding sphere) layout, vertex-chunk header bits including skinning fields (ninja_offset/ninja_weight, weight = raw/255), tiny-texture-chunk bitfields (mip depth, clamp/flip, tex_id/supersample/filter), material-chunk alpha-blend fields, and strip-chunk bitfields (double-sided, flat-shading, env-mapping, two UV-range chunk-head variants - 0-255 vs. 0-1023). Worth a full pass against this addon's own nj.py/njcm.py if their coverage is ever in question.

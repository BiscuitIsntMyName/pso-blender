pso-blender local wiki / xvm

.xvm documented, implemented (import + export) - the deepest-worked format here

Texture archive - an ordered array of Xvr (texture) entries, referenced by array position from a paired .xj's TEXTURE_ID render state. This is the format most of this fork's own work has gone into (texture-pack workflow, DXT1 encoder accuracy, content-addressed dedup).

Confirmed - pixel formats

  • Decodes: DXT1, DXT2, DXT3, DXT4, DXT5, R5G6B5, A1R5G5B5, A8R8G8B8 (16-bit formats and A8R8G8B8 use the D3D byte-order convention, B/G/R/A in memory).
  • Encodes (on export): DXT1 (opaque or punch-through alpha) or DXT2 (smooth, premultiplied alpha) - whichever matches the source image's alpha mode - or raw A8R8G8B8 if the material's "Force Uncompressed" checkbox is set (see below).
  • DXT2/DXT3 share DXT1's exact RGB color-block structure - confirmed in code (dxt3_compress_block calls dxt1_compress_block for the color block unchanged). The extra bytes in DXT2/3 go entirely to explicit 4-bit alpha, never to RGB precision - a common misconception, worth stating plainly since it looks like it should be "the higher quality one".
  • DXT1's 4-colors-per-4x4-block limit is a real, information-theoretic constraint - confirmed the original game itself works around it for a handful of its own textures by storing them uncompressed (16-bit R5G6B5/A1R5G5B5) instead of DXT1 (observed on real map data: aforest01 has 2 of 49 textures stored this way - noise/foam-pattern content DXT1 genuinely can't represent well).

Confirmed - two real DXT1 encoder bugs found and fixed

  • Palette rounding: the two interpolated DXT1 palette colors were computed with integer floor division instead of rounding, while the decoder reconstructs them with exact floating-point interpolation (never floors) - encode-time pixel classification was working off colors systematically darker than what actually gets displayed, biasing reconstruction brighter. Fixed via round().
  • palette[0:3] vs palette[0:4] (bigger impact): opaque-mode blocks only ever considered 3 of DXT1's 4 available palette colors when classifying pixels, silently wasting a quarter of the format's already-tight color budget on almost every block in the file. Fixed: palette[0:3] if block_needs_alpha else palette. Together, these two fixes dropped acity's count of "visible artifact" (single-channel-spike) textures from 53 to 2.
  • An exact "cluster fit" endpoint-selection algorithm was tried as a further improvement (more accurate on the 2 remaining hard cases) but found ~4x slower on a full map export with no viable adaptive shortcut - reverted in favor of the original fast PCA-projected-endpoints heuristic, relying on Force Uncompressed for the genuinely hard remaining cases instead.

Confirmed - export architecture

  • Xvr.id is internal bookkeeping only - never used as a cross-reference key by this addon's own read/write pipeline. The real cross-reference is the raw array position (TEXTURE_ID render state in .xj is a plain index into the .xvm's texture array).
  • Two distinct stashed identifiers, easy to confuse: xj_settings.pso_id (on materials) = the original file's real Xvr.id; pso_orig_tex_id (on images) = the original ARRAY POSITION. Different purposes.
  • Content-addressed deduplication (TextureRegistry, texture_checksum()): the original game format never duplicates texture content (confirmed: 0 duplicates across 246 real acity entries) regardless of how many places an animation is placed - export now matches that instead of writing one entry per placement.
  • Position-preserving export: since TEXTURE_ID is a raw index, dropping an original array position the current scene doesn't reference would silently corrupt any other map file sharing that same .xvm. Untouched positions get passed through byte-for-byte via Texture.prebuilt_xvr (built from xvm.read_raw(), raw compressed bytes) instead of being decoded and re-encoded - avoids introducing lossy DXT recompression noise on content nothing actually edited.
  • Texture.id vs Texture.animation_instance_id: deliberately separate - .id identifies CONTENT (shared across placements with byte-identical frames), .animation_instance_id identifies the ANIMATION INSTANCE (always unique per placement, so two placements sharing identical frame content still get independent .tam timing records).

Cross-reference: pso_ultimate_importer

  • Its xvr_load (_archives/pso_ultimate_importer-main/__init__.py:312) confirms the same container shape our own xvm.py already implements: an XVMH header magic, followed by XVRT-tagged texture chunks - consistent, no correction needed.
  • Open discrepancy, not yet resolved: their code's comment maps the format-2 compression-type field as 6=DXT1, 7=DXT3, 8=DXT5. This addon's own XvrFormat enum (xvm.py) uses DXT1=6, DXT2=7, DXT3=8, DXT4=9, DXT5=10 - a full step off from theirs starting at 7. Our own DXT1/ DXT2 values are heavily battle-tested this session (hundreds of real textures, several rounds of pixel-accuracy verification); pso_ultimate's reader is also a simplistic 3-way fallback (if 7: dxt3 elif 8: dxt5 else: dxt1) that never distinguishes DXT2/DXT4 at all, so it's plausibly just an imprecise comment rather than evidence our own values are wrong - but worth a deliberate sanity check someday rather than dismissing outright.

Verification method that actually works

  • Comparing exact compressed-byte hashes between an original and a re-exported file gives false negatives for "is this content present" whenever any DXT recompression is involved, even for correctly-represented content. Decoded-pixel comparison (average/signed/ per-channel diff, or average-color proximity) is the reliable technique - learned the hard way, twice, this session.

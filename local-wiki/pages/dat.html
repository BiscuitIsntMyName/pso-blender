.dat field layout + door mechanism confirmed via newserv, cross-checked on real data

Per-map, per-area placement data, found inside .gsl. Comes in two flavors sharing the naming pattern <map>_<area>e.dat (enemy/NPC) and <map>_<area>o.dat (object placement - doors, props, switches...). Investigated 2026-08-30 on forest01, pulled straight out of Data.gsl via gsl.py (no Blender needed for this kind of analysis).

Confirmed - two independent methods agree

  • Record size found first by our own exact file-size divisibility + repeating-header check (not assumed from any doc): 72 bytes/record for e.dat, 68 bytes/record for o.dat. Example (forest01, area 00): _00e.dat = 4824 bytes / 72 = 67 enemy records, _00o.dat = 7412 bytes / 68 = 109 object records.
  • Independently confirmed by newserv (an actively maintained open-source PSO server reimplementation with real, working parsing code - not a forum recollection): its ObjectSetEntry struct is exactly 0x44 = 68 bytes, its EnemySetEntry struct is exactly 0x48 = 72 bytes. Two unrelated methods (byte-count arithmetic on our own real files vs. an independent codebase's struct definitions) landing on the same sizes is a solid confirmation, not a coincidence. Source: src/Map.hh, src/Map.cc.

Confirmed - field layout, verified directly against newserv's real source (cloned locally to _archives/newserv, not just a summary)

Position is room-relative, not world space - per newserv, must be rotated/translated by the owning room's angle/offset (which live in the matching .rel).

OffsetObjectSetEntry (68 bytes)
0x00u16 base_type - the object type ID (door types, props, switches - see table below)
0x02u16 set_flags (runtime-only, unused in the file)
0x04u16 index (runtime-only)
0x06u16 floor
0x08u16 entity_id (runtime-only, = index + 0x4000)
0x0Au16 group
0x0Cu16 room
0x0Eu16 unknown_a3
0x103x float32 pos (X/Y/Z, room-relative)
0x1C3x u16 angle (0 = none, 0xFFFF ≈ full turn)
0x28float32 param1
0x2Cfloat32 param2
0x30float32 param3
0x34i32 param4 - for doors, the switch-flag number (see below)
0x38i32 param5
0x3Ci32 param6 - for the Forest door, 1 enables the unlock cutscene
0x40u32 unused (runtime-only pointer)

EnemySetEntry (72 bytes) is the same shape with an extra num_children/wave_number/wave_number2 up front, and 5 float params + 2 int16 params instead of the 3 float + 3 int32 params above.

Confirmed - door/switch object type IDs (this directly answers the original "which type ID is a door" question)

There is no single "door" type - each area/theme has its own door class(es), all using a param4 = switch_flag_number convention:

Type IDClass
0x0056TODoorLabo - Episode 2 Lab door
0x0080TObjDoor - Forest door
0x0081TObjDoorKey - key-locked door/switch (Forest/Cave/VR)
0x00C1 / 0x00C2TODoorCave01/TODoorCave02 - Caves doors (multi-switch / standard)
0x0100 / 0x0102TODoorMachine01/TODoorMachine02 - Mines doors (0x0102 reused for the Ep4 desert door)
0x0130TODoorVoShip - post-Vol Opt ruins door, reads quest flags directly, not switch flags
0x0144-0x014BTODoorAncient01-09 - Ruins doors
0x01A0 / 0x01AB / 0x01C0Temple/Spaceship doors (TODoorVS2Door01/TODoorFourLightRuins/TODoorFourLightSpace)
0x0202 / 0x0204TObjDoorJung/TODoorJungleMain - CCA doors (0x0204's switch sets one of 3 quest flags it checks directly)
0x0221 / 0x0222Seabed multiplayer doors (TODoorFourLightSeabed/...SeabedU)
0x0046-0x0049, 0x0054City doors (shop/guild/Ragol warp/med center/lobby-blocker) - no params
0x0090TOKeyGenericSw - generic switch for non-door triggers (lights, poison rooms, bridges)

Correction to our own earlier guess: type 0x88 (the dominant type in forest01 area 00, 49 of 109 records) is not a decorative prop as first assumed - per newserv it's TObjContainerBase2, an item/drop box.

Important caveat, seen directly in the real table: base_type IDs are not globally unique - the same numeric ID means a completely different object depending on area (and sometimes game version). E.g. 0x00C1 is TODoorCave01 in the Caves but the De Rol Le boss controller (TBoss2DeRolLe) on that boss floor; 0x0100 is TODoorMachine01 in the Mines but an NPC (__MOMOKA__) in the City. Any future parser needs the area (and ideally game version) alongside the type ID to look up the right meaning - a lookup table keyed on type ID alone would be wrong in general, even though it's usually right within one theme.

Confirmed - other common non-door object type IDs

Found while testing on real acity data (2026-08-30): a user importing acity's o.dat objects noticed many of them looked like player spawn points - confirmed directly in newserv's source, not a guess:

Type IDClass
0x0000TObjPlayerSet - defines where a player starts when entering a floor. param1 = client ID (0-3), param4 = source type (0 = arriving from a lower floor, 1 = from a higher floor).
0x0001TObjParticle - particle effect, not constructed in split-screen.
0x0002TObjAreaWarpForest - triangular cross-floor warp (param4 = destination floor).
0x0003TObjMapWarpForest - triangular intra-floor warp (param1-3 = destination coords, param4 = destination angle).
0x0008TObjEvtCollision - event collision object, triggers a wave event when a player is nearby (param1 = radius, param4 = event ID).
0x000ETObjRoomId - sets a player's room ID when nearby (used for split-screen/room-scoping logic).
0x0082TObjLazerFenceNorm - laser fence, param4 = switch flag, param6 = model (short/long).
0x0084TLazerFenceSw - laser fence switch, param4 = switch flag, param6 = color.
0x0087TMotorcycle - small vehicle prop.
0x0088TObjContainerBase2 - item/drop box (the type earlier mistaken for a decorative prop, see correction above).
0x008DTOCapsuleAncient01 - capsule/container, param6 = quest label called when activated.
0x008ETOBarrierEnergy01 - energy barrier, param4 = switch flag + activation mode.
0x0092TObjContainerBase - large box (specialized drops), same params as 0x0088.

All confirmed directly in _archives/newserv/src/Map.cc's dat_object_definitions table - this is the same list pso_blender/dat.py's KNOWN_OBJECT_TYPE_NAMES ships with.

Confirmed - filename suffix convention (game mode)

newserv's SetDataTable::map_filename_for_variation builds the filename as <area basename><o or e><game-mode suffix>.dat (or .evt for events, no o/e letter). The game-mode suffix - applied only to the floor-0 file - is: nothing for Normal, _s for Solo, _c1 for Challenge, _d for Battle (PSO's PvP mode). This explains the d-suffixed files seen alongside forest01's area files (map_forest01d.dat et al.) - they're the Battle-mode variant.

Not covered by this table, still unexplained: the _off/_offe suffix this addon found on its own (see below), and the _gjo/ad suffixes seen in forest01's file listing (e.g. map_forest01_gjo.dat, map_forest01ad.dat) - newserv's filename-generation code has no matching pattern for any of these (checked directly - no "_off" string anywhere in its source, no BB-specific override of map_filename_for_variation). Still open.

User's hypothesis (2026-08-30), plausible but not confirmed: _off = "offline" - Blue Burst has a "one person" mode similar to an offline/solo session, and if only one player is in the game the placed elements (enemy count especially) probably change accordingly. Fits the observed data well (the _off enemy set is a strict subset of the normal one, exactly the shape you'd expect from "fewer enemies for fewer players"). Doesn't map onto newserv's own _s (Solo) suffix by name, so either Ephinea's real client files use a different naming convention than what newserv's internal filename-generation logic assumes, or this is a distinct concept from newserv's Solo mode - unresolved either way.

Confirmed - the _off mechanism

  • Disambiguating result, our own data: the _off enemy file is a byte-identical ordered subsequence of the normal file (same 72-byte records, verbatim, just fewer of them - 32 of 67 for area 00) - not an edited copy, purely a subset. Combined with the .evt finding that the two variants' event data is 100% byte-identical, this means "off" mode is purely "spawn fewer enemies", not a change to any door/object logic.
  • Objects (o.dat) never have an _off variant at all, consistent with that reading.

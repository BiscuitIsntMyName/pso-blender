pso-blender local wiki / bml

.bml documented, implemented (import + export)

Container for NPCs, objects, and items - the door/prop meshes seen scattered through Data.gsl. Import needs both the .bml and its matching .xvm selected together in the file picker.

Confirmed

  • Multi-item archive with optional PRS compression: BmlHeader carries a file_count and a compression_type byte (CompressionType.NONE or CompressionType.PRS, literally the ASCII byte 'P'). A FileDescription table (32-byte name + compressed/decompressed size fields, one entry per item) follows the header; each item's actual payload is PRS-decompressed on read if the header says so - see .prs.
  • Each decompressed item's payload is itself a sequence of IFF-style chunks (iff.py) - parse_bml walks them to pull out one item's models (plural - an item can bundle more than one), texture list, texture archive, and animation data (BmlItem).
  • The per-item models found inside those chunks are the classic NJ/NJCM chunk-based Ninja model format, not the .xj vertex-buffer format map render geometry uses - two different mesh formats despite both living under this addon's "model" umbrella.
  • File alignment inside the archive differs depending on whether the archive carries textures (0x20-byte alignment) or not (0x800-byte, i.e. one CD-ROM sector - the same sector-addressing heritage as .gsl).

Cross-reference: pso_ultimate_importer

  • Its own bml_read (_archives/pso_ultimate_importer-main/__init__.py:3005) is explicitly documented as "Parse a BML archive (DC / GC PSO model bundle)" - a fixed 0x40-byte-per-entry table at offset 0x40, one PRS blob per entry (not one for the whole archive), and a texture archive appended right after its model in the stream. That's a genuinely different shape from this addon's own header/FileDescription-table/IFF-chunk structure above - but expected, not a red flag: their code is explicitly scoped to Dreamcast/GameCube .bml, this addon's is Blue Burst (PC)-only. Different platforms, apparently different archive-level layout for the same conceptual container.
  • Their shared classic-chunk reader (NinjaChunkMixin.readChunks, used for DC/GC .nj/.gj content pulled out of a .bml) confirms the classic NJ/NJCM opcode shape referenced on the NJ page: an end-of-chunks marker (NJD_CE), a no-op/continue marker (NJD_CN), and typed vertex/strip chunks in between - consistent with treating NJ/NJCM as a genuinely different mesh encoding from this addon's own .xj vertex-buffer format.

Cross-reference: newserv + Sylverant, triangulated

  • newserv's own src/BMLArchive.{hh,cc} (read directly from the local clone, _archives/newserv) confirms the same DC/GC-style layout pso_ultimate_importer described - exact fields: a 0x40-byte header (4 bytes unknown, u32 num_entries, 0x38 bytes unknown) followed by 0x40-byte entries (32-byte ASCII filename, u32 compressed_size, 4 bytes unknown, u32 decompressed_size, u32 compressed_gvm_size, u32 decompressed_gvm_size, 0x0C bytes unknown), entry data 0x20-aligned. Its constructor takes a single big_endian bool (covering both little-endian DC/PC-v1 and big-endian GC with one template), but has no separate BB variant at all - and isn't actually instantiated anywhere else in newserv's own codebase (no other call site found), suggesting it's unused/incomplete tooling there rather than a battle-tested path, unlike the very actively-used Map.cc.
  • github.com/Sylverant/pso_tools's bmltool/bmltool.c gives a third, slightly different variant: a 64-byte bml_entry_t (32-byte name + compressed/unknown/decompressed/pvm_compressed/pvm_decompressed sizes + 12-byte padding), header byte 8 required to be ASCII 'P', PVM (not GVM) texture fields - this is the PC v2 / Dreamcast variant specifically, a third distinct archive-level layout alongside the DC/GC one and this addon's own BB one.
  • Concrete, independent confirmation that BB really is a fourth, different layout: a pioneer2.net forum post (in a "State of model swapping" thread) states outright that Sylverant's bmltool "was only written for the earlier versions of PSO's files (PSO for PC and PSO for Dreamcast), and doesn't work with Blue Burst files." That's solid, if indirect, evidence this addon's own header/FileDescription-table/IFF-chunk reading (which does work against real Ephinea files) reflects a genuinely distinct BB-specific layout, rather than a bug relative to what these other two sources describe - though no source found so far documents BB's exact bytes directly, so this remains "strongly corroborated," not "independently verified byte-for-byte."

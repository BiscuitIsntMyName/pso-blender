Confirmed - the full event lifecycle (per newserv's source comments, consistent with what we observe)

  1. The event is triggered (via a quest script, or a trigger object elsewhere in .dat) - sets flags bit 0004 (runtime-only, not stored in the file).
  2. The client waits delay frames, then constructs every enemy in .dat whose room/wave_number match this entry's - sets bit 0002.
  3. The player kills all the enemies - sets bit 0010.
  4. One frame later, the post-wave action-stream program at action_stream_offset runs - sets bit 0008, then clears bit 0004 (but not 0002).

Also confirmed: event_id is not required to be unique - if several entries share an ID, triggering any one of them triggers all of them simultaneously, since wave events can only be triggered by ID.

Confirmed live and semantically coherent on forest01_00.evt: entry 0's program (0c 57 04 00 00 01) is trigger_event 0x457 = 1111 - literally entry 1's own event_id. This is a wave-completion chain: killing one wave's enemies triggers the next wave's event. set_switch_flag (e.g. 0a 05 00 = set flag 5) is directly present too - this is the concrete door/switch mechanism: a door object's param4 (see .dat) names the flag number a matching set_switch_flag/clear_switch_flag here will open/close it.

Confirmed - what the _off byte-identity finding actually means

  • Given the mechanism above, the earlier finding that _off.evt is 100% byte-identical to its normal counterpart now has a clean explanation: .evt content doesn't encode an "on" and an "off" version of anything - the event/trigger logic is the same either way. The only thing that differs between the two modes is which enemies get placed (the _offe.dat subset). Whatever "off" represents (still not confirmed - quest flag, difficulty variant, or something else), it operates purely at the enemy-placement level, not through this event-script mechanism.
